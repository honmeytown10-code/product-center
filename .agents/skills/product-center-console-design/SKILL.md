# 商品中心全域 Web 后台设计

把“属于现有商品中心、能高效完成经营任务、可直接接入真实工程”作为首要标准。本 Skill 适用于商品中心下的全部 Web 页面，价格体系只是其中一个专项模式，不能作为其他模块的默认模板。不要把页面做成通用 SaaS 模板、电商 C 端卡片流或独立 Dashboard。

## 开始前

1. 读取 [design-foundation.md](references/design-foundation.md)，应用全局外壳、密度、色彩、间距和状态规则。
2. 读取 [product-page-patterns.md](references/product-page-patterns.md) 的“业务域与线上模块地图”，再只读取当前业务域对应章节；不得因为参考链接来自价格体系就默认使用策略卡片。
3. 实现生产代码或高保真原型前读取 [implementation-rules.md](references/implementation-rules.md)。
4. 完成后用 [review-checklist.md](references/review-checklist.md) 逐项验收。
5. 设计商品中心 Next 页面时同时读取 [approved-ui-and-workflow.md](../product-center-next-design/references/approved-ui-and-workflow.md)，继承已确认的菜单、页面分型、共享 UI/交互和完成标准。

不要一次加载无关资料；只读取与当前任务对应的章节。

## 标准工作流

### 1. 建立页面上下文

先从需求和仓库推导以下信息，不因缺少完整表单而停工：

```yaml
businessDomain: 商品管理 | 分类属性 | 配方营养 | 模板同步 | 经营规则 | 价格体系 | 门店商品 | 平台商品映射 | 商品设置 | 操作日志
productArea: 商品档案 | 配方管理 | 商品运营 | 门店商品 | 平台商品管理 | 商品设置
pageType: 列表 | 配置 | 创建编辑 | 详情 | 选择器 | 弹窗 | 日志
accountView: 集团 | 品牌 | 门店
targetApp: goods-vue 或当前商品中心项目
route: /goodsCenter/** 的真实路由
scope: 机构/门店、渠道、商品/SPU、规格/SKU
primaryTask: 用户进入页面最需要完成的动作
permissions: 页面、字段和按钮权限
referencePages: 1–3 个同业务同类型页面
```

先判断当前页面属于哪个商品中心模块，再选择骨架。优先搜索当前目录、同业务页面和已有组件；`/goodsCenter/commodityManagement` 可用于理解商品中心整体外壳和高密度对象管理，但不能替代当前模块的同类参考页。若现有页面与本文档冲突，以当前生产代码和设计系统为事实来源，并指出差异。

### 2. 先输出设计契约

写代码前先给出：

- 页面目标与主任务；
- 页面骨架和信息层级；
- 组件映射；
- 核心字段及 SPU/SKU、门店、渠道口径；
- loading、empty、filtered-empty、error、no-permission、partial-permission、submitting 状态；
- 危险操作、影响范围和确认方式；
- 尚未确认但不阻塞实现的假设。

除非用户明确只要代码，否则不要跳过这一步。

### 3. 选择单一主骨架

从以下骨架中选择一个，不混成无层级的“大杂烩”：

- 高频对象管理：紧凑筛选 + 操作栏 + 高密度表格。
- 少量复杂策略：紧凑筛选 + 说明 + 策略卡/表格 + 配置弹窗或详情。
- 长表单：基础信息 → 商品信息 → 售卖/渠道 → 适用范围 → 高级设置。
- 分类与属性：左侧树/分类，右侧列表或配置面板。
- 配方与规则：左侧对象/分组定位 + 右侧层级配置、关联关系或规则摘要。
- 门店与平台商品：范围上下文 + 商品表格 + 映射/渠道状态 + 批量操作。
- 同步任务：源/目标范围 → 映射或差异 → 校验 → 执行 → 结果。
- 操作日志：范围筛选 → 变更摘要 → 前后快照 → 操作人和时间。

### 4. 保持商品语义清晰

- 明确区分商品/SPU、规格/SKU、套餐子项、做法、加料和渠道商品。
- 门店范围与渠道范围必须可见；全局范围和局部范围不得混淆。
- 图片只帮助识别商品，不主导后台布局。
- 状态始终使用文字；颜色、图标和角标只能辅助。
- 批量操作显示已选数量、作用范围、成功数、失败数和失败原因。
- 价格、库存、上下架、沽清、同步等操作必须说明生效对象与时间。
- 删除、禁用、取消沽清、覆盖同步等高风险动作必须二次确认。

### 5. 实现并验证

- 复用目标页面同目录组件，再用业务私有组件和统一组件，最后才新增组件。
- 默认只实现业务内容区，不重复生成基座的顶部导航、商品中心左侧模块菜单、多页签或面包屑；只有用户明确要求改基座外壳时才触碰这些区域。
- 不凭记忆编造组件 Props、Events、Slots 或接口字段。
- 用真实控件实现输入、开关、分页、弹窗、树和表格；原型也要标明生产组件映射。
- 验证 1440px 基线、横向滚动、长名称、空值 `--`、真实数值 `0`、权限和异常状态。

## 输出最低要求

设计方案至少包含页面结构、组件映射、状态矩阵和关键交互。代码交付还必须说明修改文件、复用组件、验证结果及未覆盖的真实接口或权限依赖。

## 禁止事项

- 不为商品中心单独发明新主题色、渐变背景、超大圆角或营销式大标题。
- 不用卡片代替所有表格；策略类少量对象是明确例外。
- 不用普通 Select 伪装机构/门店选择器。
- 不把渠道分组当成单一操作渠道展示。
- 不只设计正常有数据状态。
- 不在视图中散落原始 URL、权限判断或大段硬编码文案。
- 不因“现代化”擅自降低信息密度或放大基础字号。
