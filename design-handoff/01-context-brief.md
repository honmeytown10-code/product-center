# 全渠道商品管理策略 — 重设计上下文包

> 这份文档是自包含的。把它整份贴进 claude.ai/design，Design 无需访问代码仓库即可理解本页面的业务模型、现状实现、设计约束与改版目标。

---

## 1. 产品背景

企迈「商品中心」是餐饮连锁品牌的商品管理后台，运行在 Console 2.0 基座内（顶部导航 + 左侧模块菜单由基座提供，**本页只设计业务内容区**）。

本页面是**品牌级的一次性经营配置**，路径为：商品中心 → 商品设置 → 全渠道商品管理策略。

它不是日常高频页面，而是「决定整个商品中心怎么运转」的开关面板 —— 用户在这里做的选择会改变：
- 商品资料在哪里维护（商品主档 / 渠道商品库 / 三方平台）
- 商品中心左侧菜单显示哪些模块（渠道商品库、商品映射等会随策略出现或消失）
- 谁有权限管哪些渠道的商品

**核心张力**：配置项数量不多（两个 section），但每个选择的下游影响面极大，而当前设计几乎没有表达这种影响。

## 2. 业务模型（Design 必须理解的概念）

### 2.1 渠道（Channel）

共 9 个渠道，分两类：

**自有渠道（private，共 3 个）** —— 永远由企迈管理，不可切换：

| id | 名称 |
|---|---|
| `pos` | POS |
| `mini_program_dine_in` | 小程序堂食 |
| `mini_program_delivery` | 小程序外卖 |

**三方渠道（third_party，共 6 个）** —— 每个都要选择由谁管理：

| id | 名称 | 商品作用域 | 备注 |
|---|---|---|---|
| `meituan` | 美团外卖 | 仅门店级 | 支持服务商计费 |
| `taobao` | 淘宝闪购 | 仅门店级 | 支持服务商计费 |
| `jingdong` | 京东外卖 | 仅门店级 | |
| `douyin` | 抖音在线点 | 品牌级 + 门店级 | 需品牌审核 |
| `meituan_dine` | 美团在线点 | 品牌级 + 门店级 | |
| `meituan_pinhaofan` | 美团拼好饭 | 仅门店级 | |

> 注意：`platformProductScope`（品牌级/门店级）和 `requiresBrandReview`（需品牌审核）这两个业务属性目前**在界面上完全没有体现**，但它们真实影响用户操作路径。这是改版可以补上的信息。

### 2.2 配置项一：组织协作方式（collaborationMode）

品牌二选一：

- **`unified` 统一商品维护** —— 商品身份、结构、渠道售卖资料在同一个商品入口维护，一次保存完成。系统自动生成一个「品牌默认商品库」，覆盖所有企迈管理的渠道。
- **`channel_division` 按渠道职责协作** —— 按堂食 / 外卖 / 在线点等职责建立多个「渠道商品库」，通过角色权限控制各团队管理范围。

选 `channel_division` 时，必须把**每一个企迈管理的渠道**分配进某个渠道商品库分组，且**一个渠道只能属于一个分组**。有未分组渠道时不允许保存。

默认数据（三个分组）：

| 分组名 | 包含渠道 |
|---|---|
| 堂食商品库 | POS、小程序堂食 |
| 外卖商品库 | 小程序外卖、美团外卖、淘宝闪购、美团拼好饭 |
| 在线点商品库 | 抖音在线点、美团在线点 |

### 2.3 配置项二：三方渠道管理策略

每个三方渠道独立选择「商品资料维护位置」：

- **`qimai` 企迈管理** —— 商品资料在企迈维护并发布到平台。企迈能力**强制固定**为「企迈接单」+「商品发布、上下架与库存」，不可勾选调整（界面上显示为两个绿色只读标签）。该渠道会进入渠道商品库分组体系。
- **`platform` 平台管理** —— 商品售卖资料由三方平台自己维护，商品中心只生成企迈侧渠道商品。此时用户**可以按需勾选**企迈参与哪些能力：
  - `order_receiving` 企迈接单
  - `product_operations` 上下架/库存
  - 两个都不勾 = 仍允许通过模板或发布中心下发企迈侧门店渠道商品，但暂不启用接单、上下架或库存能力，也不要求门店绑定

**联动规则**：
- 从 `qimai` 切到 `platform` → 该渠道停止由企迈维护和发布平台专属资料，但保留当前企迈经营能力；只要仍启用接单或上下架/库存，就继续归属渠道商品库、下发企迈侧门店渠道商品并建立映射。仅在关闭全部企迈经营能力后，才从商品库分组中移除并取消门店绑定要求。
- 从 `platform` 切到 `qimai` → 能力被强制设为两个全开。
- 「门店连接要求」是**派生状态**，不可直接编辑：`qimai` 模式，或 `platform` 模式下勾选了任一能力 → 显示「需门店绑定」；否则「无需绑定」。
- 门店绑定、授权方式、平台接口费用都在**另一个系统**（门店绑定中心 `console.qmai.co/commonCenter/takeaway/binding`）配置，本页只做外链跳转。

### 2.4 下游影响（当前界面完全没有表达）

保存后会实际改变的东西：

| 策略 | 下游影响 |
|---|---|
| 任一渠道切到 `platform` | 企迈不再发布平台商品资料；模板仍可下发企迈侧门店渠道商品，启用接单、上下架或库存后通过映射衔接平台真实商品 |
| 有企迈管理渠道 | 商品中心出现「渠道商品库」模块 |
| `unified` 模式 | 商品编辑页合并为单一入口，渠道售卖字段内联 |
| `channel_division` 模式 | 商品编辑拆分为主档 + 各渠道商品库，按角色分权 |
| 渠道分组变更 | 该渠道下已有的渠道商品资料归属发生迁移 |
| 商品模板下发 | 若模板覆盖的渠道跨越多个商品库，会被拒绝并提示「请拆分为不同模板」 |

### 3.2 现状交互与状态

- 页面用本地 `draft` state，改动**不立即生效**，点「保存策略」才写入。
- 分组弹窗内的增删改也只改 `draft`，关闭弹窗不丢失，但仍需外层「保存策略」才落库。
- 删除分组用的是浏览器原生 `window.confirm`。
- 校验只有两条：① `channel_division` 下有未分组渠道时阻止保存；② 分组名或适用渠道为空时阻止保存分组。
- 反馈全部走同一个 `feedback` 字符串，渲染在页面顶部橙条。

## 4. 设计规范（必须遵守）

来自企迈商品中心设计基线：

### 视觉 Token

| 项目 | 规则 |
|---|---|
| 基础字号 | 14px |
| 辅助文字 | 12px |
| 页面/面板标题 | 16–20px，**禁止营销式大标题** |
| 默认行高 | 24px |
| 控件尺寸 | 统一使用组件库的 `small` 号 |
| 间距 | 只能从 4 / 8 / 12 / 16 / 24px 中选 |
| 内容区外边距 | 12px |
| 白色容器圆角 | 8px（**禁止 16–24px 大圆角**） |
| 设计基准宽度 | 1440px，内容需在 1180–1240px 可用宽度内稳定 |

### 色彩

```css
--colorPrimary: #00b460;        /* 品牌绿，主操作/选中态 */
--colorText: rgba(0,0,0,0.88);
--colorTextSecondary: rgba(0,0,0,0.65);
--colorBgContainer: #fff;
--colorBgLayout: #f5f5f5;
--colorBorderSecondary: #f0f0f0;
```

现状代码里的硬编码色值（作为视觉证据）：
`#1D2129` 主文字 / `#4E5969` 次文字 / `#86909C` 弱文字 / `#E5E6EB` 边框 / `#C9CDD4` 控件边框 / `#F7F8FA` 表头灰 / `#F5F6F8` 页面底 / `#00B460` 主绿 / `#F2FFF8` 选中浅绿 / `#D46B08` + `#FFF7E8` 警示橙 / `#F53F3F` 必填红 / `#CB2634` 危险红

规则：
- 红色**只**表达失败、危险、异常、负向结果。
- 状态**不能只靠颜色**表达，必须有文字。
- 不把渠道品牌色当页面主题色。

### 必须设计的页面状态

loading / success / first-empty / filtered-empty / error / no-permission / partial-permission / submitting / partial-success

### 商品设置类页面的专门规则

- 通用设置按能力分组，**展示当前值、默认值、作用范围和修改后生效方式**。
- 全局/品牌/门店级配置不得混在同一层级而不显示继承来源。
- 设置项多时用左侧分组或锚点导航，右侧保持单列稳定表单。
- **修改影响历史商品或下游渠道时必须先解释影响范围，再允许保存。**

### 明确禁止

- 不发明新主题色、渐变背景、超大圆角、营销式大标题
- 不用卡片代替所有表格
- 不用普通 Select 伪装机构/门店选择器
- 不把渠道分组当成单一操作渠道展示
- 不只设计正常有数据状态
- 不因「现代化」擅自降低信息密度或放大基础字号
- 不重复设计基座的顶部导航、左侧菜单、多页签、面包屑

## 5. 现状的问题（改版要解决的）

1. **没有影响预览**。这是一个改一下就会重排整个商品中心工作流的页面，但保存前用户看不到「我这次改动会导致什么」。设计基线明确要求「修改影响下游渠道时必须先解释影响范围」。
2. **两个 section 是并列的，但实际有依赖关系**。三方渠道选了「企迈管理」才会进入渠道商品库分组体系；协作方式选了 `channel_division` 才需要分组。现在这个因果关系要用户自己在脑子里拼。
3. **分组管理被藏进弹窗**。渠道商品库分组是这个页面信息量最大、最需要通盘看的部分，却塞在一个 920px 弹窗里，还要在弹窗内再做左右分栏 + 二级编辑态，层级过深。
4. **「企迈管理」模式下能力是只读的两个绿标签**，和「平台管理」下的可勾选 checkbox 视觉相近，用户容易误以为可点。
5. **渠道的业务差异没有暴露**：品牌级 vs 门店级作用域、是否需要品牌审核、是否涉及服务商计费，这些都会影响用户决策，但界面上完全不可见。
6. **9 个渠道里只有 6 个出现在表格里**。POS 和两个小程序渠道（永远企迈管理）只在分组弹窗里出现，用户没有一个地方能看到「我品牌全部 9 个渠道现在各是什么状态」。
7. **状态覆盖不全**：没有 loading、没有权限态、没有保存中态；删除确认用的是原生 `window.confirm`；所有校验反馈挤在页面顶部一个橙条里，不定位到出错的具体控件。
8. **保存是全页一次性提交**，但两个 section 的变更风险等级完全不同（切换协作方式 >> 调整某个渠道能力勾选）。

## 6. 改版目标

产出**高保真原型 / Mockup**，用于团队评审对齐视觉与交互方案，暂不落地代码。

期望覆盖：
1. 页面主骨架的重新组织 —— 让「协作方式 → 渠道归属 → 三方策略」的因果链在版面上成立。
2. 渠道全景 —— 一个地方看清 9 个渠道各自的管理方 / 所属商品库 / 企迈能力 / 绑定要求。
3. 分组管理的位置与形态重新决策（是否还该是弹窗）。
4. 保存前的影响范围说明 / 变更确认。
5. 完整状态矩阵（含空态、权限态、提交态、校验错误定位）。
6. 只读 vs 可编辑的视觉区分。
